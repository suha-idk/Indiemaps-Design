# Build Raahi — A Voice-First AI Navigation Copilot for India
## Frontend-Only MVP Design and Interactive Prototype

Act as a world-class product designer, senior frontend engineer, and UX specialist who has designed navigation products comparable to Google Maps, Waze, Uber Driver, and Rapido Captain.

Design and implement a polished, highly intuitive, mobile-first frontend for **Raahi (राही)**, a voice-first AI navigation copilot designed primarily for Indian taxi drivers, auto-rickshaw drivers, bike riders, delivery partners, commercial drivers, and everyday commuters.

**IMPORTANT: Build the frontend and interactive prototype only. Do not implement a backend, database, authentication system, AI model integration, MCP server, external API integration, or real navigation calculations.** Use realistic mock data and local frontend state to demonstrate how the finished product will behave. Structure the UI cleanly so that real Google Maps, Gemini, speech recognition, and routing services can be integrated later.

Do not create a generic dashboard, a generic AI chat interface, or a landing page. Build the actual navigation application.

---

# 1. Product vision

Raahi lets a driver control a journey by speaking naturally in their preferred language.

A driver should be able to open the app, see the map, tap one large microphone button, and say something like:

- "Mujhe Connaught Place se Rohini jaana hai."
- "Beech mein ek CNG pump add kar do."
- "Airport jaane se pehle Dhaula Kuan par rukna hai."
- "Toll road mat lena."
- "Find the nearest petrol pump along my route."
- "Add a chai stop, but don't increase my journey by more than ten minutes."
- "Destination change karke India Gate kar do."
- "Sabse fast route batao."
- "Avoid traffic and find another route."
- "Mujhe ghar le chalo."
- "Raste mein ek passenger pickup karna hai."
- "Take me to Rohini, but avoid tolls and highways if possible."

The UI should communicate that the copilot understands the driver's intention, updates the journey, and reflects the change visually on the map.

The driver must not need to navigate complex menus or repeatedly type addresses.

**Core product principle: Voice first, map always visible, controls simple, driver remains in control.**

---

# 2. Target audience and usability requirements

Design for two overlapping audiences:

1. Drivers who are not comfortable with technology, may have limited experience with complicated apps, and prefer speaking their native language.
2. Technology-savvy drivers who already understand navigation apps but want to save time by controlling routes through natural language.

Many users will use Android phones mounted on their vehicles. The product must also work well in a desktop browser for team demonstrations.

Prioritize:
- Very large, easy-to-understand controls.
- Clear labels and familiar icons.
- High contrast in daylight.
- Minimal reading and typing.
- Clear voice recording feedback.
- Large tap targets, ideally 48–56 px for primary actions.
- Simple Hindi and English labels, avoiding technical jargon.
- Friendly, concise assistant responses.
- Obvious recovery actions when something goes wrong.
- No dense settings panels or unnecessary cards.
- No tiny buttons that are difficult to tap while mounted in a vehicle.

Never encourage drivers to interact with the interface while driving. Include a subtle, sensible safety reminder that drivers should make changes while safely stopped.

# 6. Voice-first AI copilot

The copilot is Raahi's differentiating feature.

It should feel like speaking to a capable assistant, not filling out a form.

## Primary microphone interaction

Create one large, unmistakable microphone button.

Use clear visual states:

1. **Ready:** "Tap to speak" / "बोलने के लिए टैप करें".
2. **Listening:** Animated microphone indicator with "Listening…" / "सुन रहा हूँ…".
3. **Processing:** "Understanding your request…" / "आपकी बात समझ रहा हूँ…".
4. **Applying:** "Updating your route…" / "रूट अपडेट हो रहा है…".
5. **Success:** "Route updated" / "रूट अपडेट हो गया".
6. **Clarification:** A concise question with one or two relevant options.
7. **Error:** A helpful, actionable recovery message.

Show a live transcript preview during recording where appropriate.

Provide a clear way to stop recording.

For this prototype, microphone interaction may use simulated speech states or existing browser speech capabilities if already available. Do not add a backend or claim that speech recognition works when it does not.

Do not force the user to type after speaking. Design the interaction so a completed voice request can be submitted automatically when the recording ends, with appropriate feedback.

Keep text entry available as a secondary alternative.

## Language support

Provide a persistent, accessible language selector:
- English
- हिंदी
- Hinglish

The UI language and spoken-command language must be conceptually separate.

A user viewing the interface in English should still be able to speak Hindi or Hinglish. A user viewing the interface in Hindi should still be able to speak English.

Localize all visible UI labels, placeholders, button text, status messages, itinerary labels, and error messages for the selected interface language.

Do not translate proper place names unnecessarily.

Provide natural, concise example assistant responses:

English:
"Done. I've added a CNG stop before your destination."

Hindi:
"हो गया। मैंने आपके गंतव्य से पहले CNG स्टेशन जोड़ दिया है।"

Hinglish:
"Ho gaya. Maine destination se pehle CNG stop add kar diya hai."

Use realistic assistant message styling with small status icons, not oversized chat bubbles.

# 9. Natural, low-friction route changes

The product should feel conversational and hands-free.

Do not make the interface show a large confirmation dialog after every simple action.

For ordinary, unambiguous commands in the prototype:
- Apply the mock change immediately.
- Update the route markers and itinerary.
- Show a small success notification.
- Offer a compact Undo action.
- Provide a brief assistant response.

Examples:
- Add a known stop.
- Remove a clearly identified stop.
- Change the destination to an unambiguous place.
- Switch route preference.
- Enable avoid-tolls preference.

For ambiguous requests:
- Ask a concise clarifying question.
- Show no more than two useful choices initially.
- Allow the user to choose a candidate.

For consequential or genuinely uncertain actions:
- Preserve the current journey and ask for clarification before applying changes.

Do not make every interaction require confirmation. Use undo and transparent status feedback for ordinary, reversible mock changes.

## Undo and recovery

After a change, display a small temporary notification such as:

"Added CNG station before Rohini. Undo"

If the user selects Undo, restore the previous itinerary and route display.

Also include a subtle recent-action indicator in the copilot so users understand what changed.

# 17. Technical implementation requirements

- Build the frontend within the existing Lovable project.
- Use React and TypeScript with reusable components.
- Use the existing project framework and conventions wherever practical.
- Use Tailwind CSS and the existing component library if available.
- Use Lucide icons or an equivalent consistent icon system.
- Keep components modular and maintainable.
- Use React state for the prototype's interactive behavior.
- Use local mock data for destinations, stops, route summaries, and nearby suggestions.
- Keep the map, itinerary, and copilot synchronized through a shared journey state.
- Use stable IDs for stops instead of array indices as permanent identifiers.
- Maintain strict separation between the final destination and intermediate stops.
- Use semantic HTML, accessible labels, keyboard support, and visible focus states.
- Ensure responsive behavior for desktop, tablet, and Android-sized screens.
- Respect reduced-motion preferences.
- Avoid unnecessary dependencies.

Do not add:
- A backend.
- Database tables.
- User authentication.
- Lovable Cloud setup.
- Gemini API calls.
- Google Maps API calls.
- Billing or API keys.
- MCP tools.
- Real geocoding.
- Real route calculations.
- Real GPS tracking.

If a map connector is already configured, do not assume it is authorized or working. Keep this task focused on the frontend design and simulated behavior.

Design components so future integrations can replace the mock services without requiring a complete redesign.

# 18. Quality standards

The result should look and feel like a credible, well-designed navigation MVP.

Before finishing, check that:

- The map is the dominant feature.
- The interface is easy to understand without technical knowledge.
- The microphone is the most obvious interaction.
- The route summary is always easy to find when a journey exists.
- The copilot does not dominate the map.
- The interface is fully bilingual at minimum in English and Hindi, with Hinglish command examples.
- The language toggle does not reset application state.
- Adding or removing a stop updates the itinerary and map together.
- The final destination never changes accidentally.
- Undo restores the previous state.
- Route preferences visibly update.
- The prototype works on laptop browsers and narrow mobile screens.
- All visible buttons have meaningful actions.
- Empty, loading, and error states are designed.
- The app uses consistent design tokens and polished typography.
- The simulated map and data are never misrepresented as live navigation.

**Final instruction:** Build the actual frontend now. Do not merely return a design plan, a product specification, or a written description. Implement the UI and its core mock interactions in the Lovable project. Preserve any existing working project configuration and avoid rebuilding unrelated infrastructure.
